数仓最怕的不是任务跑挂——挂了会报错，你立刻知道。真正可怕的是它**悄悄跑错**：任务绿灯、数据照出，只是数字已经不对了，而下游还在拿它做决策。等业务发现"这数不对劲"，往往已经错了好几天。

> 坏数据比没数据更可怕。没数据你会去查；坏数据你会**照着它做判断**。数据监控的意义，就是让"悄悄坏掉"变成"第一时间报警"。

<div class="keypoint">
<div class="lbl">监控就在回答三个问题</div>
<p>一张表健不健康，说到底就三问：<strong>它还全吗</strong>（数据没缺）、<strong>它还新吗</strong>（按时更新了）、<strong>它还准吗</strong>（量级、分布、主键都正常）。下面的维度、告警、血缘，都是围绕这三问展开。</p>
</div>

## 一、先盯住数据质量的几个维度

监控不是"看任务成没成功"，而是看**数据本身对不对**。几个最常翻车的维度：

- **完整性 / 空值**：关键字段的空值率是否突然飙升。*比如*订单表的 `user_id` 平时空值 0.1%，今天变 30%，多半是上游埋点或 join 出了问题。
- **量级突变**：行数 / 新增量是否异常。*比如*每天稳定进 100 万行，今天只有 10 万——上游断流；或暴涨到 500 万——重复写入。
- **主键唯一性 / 重复**：本该唯一的主键出现重复，通常是 join 炸裂或重跑没去重。这类错最隐蔽，聚合结果会悄悄翻倍。
- **新鲜度与延迟**：数据是不是按时到位（下一节细说）。
- **分布漂移**：某个维度的取值分布突变。*比如*某渠道占比从 5% 跳到 50%，即使总量没变，也往往意味着口径或映射错了。

<div class="keypoint">
<div class="lbl">落地建议</div>
<p>别想着一次把所有表都监控齐。<strong>先给核心表（下游依赖最多的那几张）配上"行数 + 空值率 + 主键重复 + 新鲜度"四项基础检查</strong>，覆盖 80% 的事故，再逐步加维度。</p>
</div>

## 二、新鲜度与 SLA

新鲜度（Freshness）是最该先上的一项：**数据有没有按约定时间到位**。

- 给每张核心表定一个 SLA：*比如*"每天 08:00 前，昨天的数据必须就绪"。
- 监控"最新分区 / 最大事件时间"离现在多久。超过阈值就报警，哪怕任务显示成功——**任务成功 ≠ 数据到位**（上游延迟、回看窗口没覆盖都会漏）。
- 有回看窗口的链路（如 GA4 这类有几天延迟的源）要按特性放宽新鲜度判断，否则天天误报。

## 三、告警怎么设：阈值 vs 同比环比

设告警的难点不是"能不能报"，是**怎么不误报又不漏报**。

- **静态阈值**：简单直接（如"行数 < 1 万就报"），适合有硬性下限的场景；缺点是业务有波动时要么太松要么太紧。
- **同比 / 环比**：和昨天、上周同一天比，偏离超过 X% 才报。更贴合有周期性的业务（周末天然低，别误报）。
- **动态基线**：用过去 N 天的均值 / 分位数算一个浮动区间。最省心，但要够多历史数据。

*经验*：核心指标用同比环比 + 合理的静态兜底（防止"缓慢滑坡"被同比掩盖），比单一阈值稳得多。

## 四、血缘与影响面

一张表坏了，真正的问题是**它牵连谁**。

- 有血缘（lineage）时，一眼看清"这张表错了，下游哪些报表、模型、看板会跟着错"，能第一时间通知到人、及时止损。
- 报警里最好带上影响面：不是干巴巴一句"表 X 异常"，而是"表 X 异常，影响下游 3 张 gold 表和 2 个看板"。收到的人才知道有多急。

## 五、监控放在哪一层

分层数仓（bronze / silver / gold）里，每层的监控重点不同：

<pre class="mermaid">
flowchart LR
  SRC["数据源"] --> B["bronze<br/>原样落地"] --> S["silver<br/>清洗建模"] --> G["gold<br/>面向业务"]
  B -.->|"量级 · 新鲜度"| M1["接入层监控"]
  S -.->|"空值 · 主键 · 分布"| M2["质量层监控"]
  G -.->|"指标同环比 · SLA"| M3["业务层监控"]
</pre>

- **bronze（接入层）**：盯量级和新鲜度——上游断没断、到没到。
- **silver（清洗建模层）**：盯空值、主键重复、分布——清洗和 join 有没有出错。
- **gold（业务层）**：盯最终指标的同比环比和 SLA——交付给业务的数对不对、准不准时。

越靠近业务，越该用"和历史比"的方式监控指标本身。

## 六、别让告警变成"狼来了"

监控最大的敌人不是漏报，是**告警疲劳**——报得太多太杂，大家就都不看了。

- 给告警分级：致命（下游停摆）、警告（需关注）、提示（记录即可），只有致命的才即时打扰人。
- 定期回收：常年误报的规则要么调阈值，要么删掉。**一个没人看的告警比没有告警更糟**——它给了你"有在监控"的错觉。
- 报警要能定位：带上表名、异常项、偏离多少、影响面，让收到的人 30 秒内能判断要不要马上处理。

## 七、用什么工具落地

上面的思路，市面上有成熟工具帮你落地，不用全手写 SQL 巡检。按角色分：

**数据质量测试（写进管道、每次跑批时校验）**：

- **dbt tests**：dbt 内置的 `not_null` / `unique` / `accepted_values` 等断言，配 **dbt-expectations** 扩展能测更细；已经用 dbt 建模的话，这是零成本起步。
- **Great Expectations**：功能最全的 Python 数据校验框架，能生成数据画像和期望套件，重但强。
- **Soda（Soda Core / Cloud）**：用 YAML 写检查（SodaCL），轻量、上手快。
- **Elementary**：dbt 原生的可观测层，直接读 dbt 的测试结果和元数据出报告。

**数据可观测性（自动学基线、发现你没想到的异常，商业为主）**：**Monte Carlo**、**Bigeye**、**Metaplane**——主打"不用手写规则，自动监测新鲜度/量级/schema 漂移并报警"。

**告警与看板**：**Grafana**（配 **Prometheus** 或直连数仓）把监控指标可视化、配告警。

**调度侧**：**Airflow** 的 data-quality operator、**Dagster** 的 asset checks 与 sensor——把检查嵌进任务流，不通过就阻断下游。

| 工具 | 类型 | 定位 | 上手成本 |
|---|---|---|---|
| **dbt tests** | 开源 | 建模管道里的断言，起步首选 | 低（已用 dbt 的话） |
| **Great Expectations** | 开源 | 全能校验框架，能力最强 | 高 |
| **Soda** | 开源 + 商业 | YAML 写检查，轻量 | 低 |
| **Elementary** | 开源 | dbt 原生可观测报告 | 低 |
| **Monte Carlo / Bigeye** | 商业 | 自动基线、免写规则 | 中（接入后省心） |

*选型粗线*：已用 dbt → 先上 **dbt tests + Elementary**；想少写规则、预算够 → **Monte Carlo 这类可观测平台**；只是要个看板告警 → **Grafana**。

## 结语

数据监控的目标不是"零故障"，而是**故障发生时你比业务先知道**。先给核心表配上最基础的四项检查、定好新鲜度 SLA、把告警控制在"每条都值得看"，剩下的再逐步加。悄悄坏掉的数据一旦能第一时间冒头，数仓才算真正靠得住。
