数仓做久了会发现：业务千变万化，但落到表上的套路就那么几种。认得这些模式，遇到新需求时不用从零想，套上去改改就行。这篇把最常反复出现的几种攒一块，每个讲清楚它解决什么问题、怎么用、坑在哪。

> 模式是前人踩坑踩出来的“默认解法”。别硬造轮子——先问“这需求是不是某个老套路”，八成是。

<div class="keypoint">
<div class="lbl">怎么用这篇</div>
<p>不用背。遇到具体问题时对号入座：<strong>要不要留历史</strong>→看 SCD / 快照 / 拉链；<strong>怎么跑得快又能重跑</strong>→看全量增量 / 幂等；<strong>怎么防止数据变脏</strong>→看去重与主键。每种模式都是一个“解决某类问题的模板”。</p>
</div>

## 一、事实表与维度表（星型模型）

数仓建模的地基：把数据拆成“**发生了什么**”和“**围绕它的描述**”两类。

- **事实表（Fact）**：记录一件件业务事件，通常又长又窄、只增不改。*比如*每一笔订单、每一次点击。字段以**度量值**（金额、数量）和**外键**为主。
- **维度表（Dimension）**：描述事实的“背景资料”，通常又宽又短。*比如*商品、用户、门店、日期。
- **星型模型**：一张事实表中间，四周挂一圈维度表，靠外键连起来——画出来像颗星。*好比*一篇新闻稿，事实表是“谁在何时干了什么”，维度表是把“谁/何时/在哪”展开成详细档案。

> 坑：别把频繁变化的描述塞进事实表。商品名改了，你不想去改历史上百万条订单——那是维度表该管的事。

## 二、缓慢变化维（SCD）

维度会变：用户换了城市、商品调了类目。**要不要留旧值**，决定了用哪种 SCD。

- **SCD Type 1（直接覆盖）**：新值盖掉旧值，不留历史。*适合*不关心过去的字段，比如修正一个拼错的名字。
- **SCD Type 2（加行留史）**：变一次加一条新记录，用“生效时间 / 失效时间 / 是否当前”标记。*适合*要回答“**下单那一刻**这个用户是哪个城市”的分析。
- **SCD Type 3（加列留史）**：只留“上一个值”一列，历史深度有限，用得少。

*好比*改简历：Type 1 是直接改掉，Type 2 是每版都存档，Type 3 是只记“上一份工作”。

## 三、快照表 vs 拉链表

两种留历史的思路，代价差很多。

- **快照表（Snapshot）**：每天把全量状态整个存一份。*好比*每天给数据拍张全家福。简单、好查“某天什么样”，但**数据量随天数线性膨胀**。
- **拉链表（Zipper / 历史拉链）**：只在**发生变化时**记一条，带“开始日期 / 结束日期”。*好比*只在搬家时记一笔地址变更，中间不动。省空间，但查询要用时间区间卡，写起来更绕。

<div class="keypoint">
<div class="lbl">快照还是拉链？</div>
<p>状态<strong>变化少、要省空间</strong>→拉链；状态<strong>天天变、或要简单可靠</strong>→快照。数据量不大时，别为省那点空间上拉链，快照更省心、更不容易写错。</p>
</div>

## 四、全量 vs 增量

每次重算全部，还是只处理新增变化？这决定了跑批的速度和复杂度。

- **全量（Full）**：每次把源表整个重算。*优点*简单、天然自愈（错了重跑就对）；*缺点*数据一大就慢、费钱。
- **增量（Incremental）**：只处理“上次之后变化的部分”，靠时间戳或自增 ID 界定。*优点*快、省；*缺点*复杂，还要处理**迟到数据**和**边界重叠**。

> 常用折中：增量为主，但留一个**回看窗口**（比如每次多跑最近 N 天），把迟到、更新的数据补齐。

## 五、幂等与可重跑

跑批一定会失败、会需要回刷。**同一批数据重跑一次，结果必须和跑一次一样**——这就是幂等。

- 关键做法：按分区**先删后insert**（overwrite 整个分区），而不是无脑 append——否则重跑就翻倍。
- *好比*铅笔写字：可重跑就是“能擦干净再写”，而不是在旧字上又描一遍。
- 做到幂等，回刷才敢放心点；否则一次重跑就制造一堆重复数据。

## 六、去重与主键

数仓里最常见的脏数据来源之一，就是**主键不唯一**。

- 先想清楚这张表的**粒度**：一行到底代表什么？“一个订单一行”还是“一个订单商品一行”？粒度定了，主键就定了。
- 去重别只 `distinct`——重复行往往字段有细微差异。常用套路：按业务主键分组，用 `row_number()` 按更新时间取最新一条。
- *好比*同一个人填了两次表，你要的不是“删掉一模一样的”，而是“认准是同一个人、只留最新那份”。

## 七、时间维度

几乎每个分析都要按时间切，所以专门建一张**日期维度表**很值。

- 预先算好每一天对应的：年 / 季 / 月 / 周、是否周末、是否节假日、财年归属等。
- *好处*：分析时直接 join 就能按“工作日”“节假日”“财年”切，不用每次现算，口径也统一。
- *好比*提前印好一本万年历，谁要按什么口径看时间，翻这本就行。

## 八、用什么落地这些模式

这些套路不用自己从头造轮子，现代数据栈里大多有现成实现：

- **dbt snapshots**：一条配置就能做 **SCD Type 2**（自动记生效/失效时间），不用手写拉链逻辑。
- **dbt incremental models**（配 `unique_key` + `incremental_strategy`）：现成的**增量 + 幂等**，重跑不叠数据。
- **分区 overwrite**（Spark / dbt / 数仓自带）：实现"先删后写"的幂等落地。
- **维度建模方法论**：星型模型、事实/维度、SCD 这套的出处是 **Kimball**《The Data Warehouse Toolkit》——想系统学建模，这本是绕不开的经典。

*一句话*：模式是"怎么想"，dbt / Kimball 这些是"怎么落地和查证"。先认套路，再挑趁手的工具实现。

## 结语

这几种模式覆盖了数仓里的大半日常：**建模**看星型 + SCD，**留史**看快照 / 拉链，**跑批**看全量增量 + 幂等，**质量**看去重与主键。遇到新表先套一遍，往往发现“这不就是个拉链 + 增量嘛”——认得套路，是数仓提速最实在的一步。数据进来前后的采集与清洗，见 [数据采集](/blog/zh-shucang-collect/) 和 [数据清洗的三个隐形坑](/blog/zh-shuju-qingxi/)。
